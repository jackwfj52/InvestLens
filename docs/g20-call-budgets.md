# G20：统一预算与调用计量

Run 的 deadline 在创建时固定为 createdAt + 120 秒，排队、执行与租约重领都不重置。处理器 Claim 收到实时 RemainingBudget，外部调用通过 BudgetedCalls 先在独立事务中保留额度并提交 tool_calls，再在事务外执行操作；Permit 向适配器传递绝对 expiresAt、timeoutMillis 及扣减后的剩余额度。派发前重新检查有效执行令牌、租约和时间。

V11 增加计量及资产窗口表，并给 Run 计数增加数据库上限。每 Run 最多三个已登记且在固定组合内的非现金资产，每资产绑定一个不可变窗口，DATA 最多八次；MODEL 最多四次非修复尝试（包含模型重试）加全局一次 Schema 修复，总共最多五次；DATA/MODEL 的重试共享两次上限。每次保留都增加总尝试数，重试和修复没有额外的隐藏额度。额度、窗口和调用记录一起提交，失败/超时不返还额度，非法请求、冲突窗口及预算不足回滚保留，不发调用。计数和窗口不依赖进程内缓存。

单次 Permit 最多行情 8 秒、模型 30 秒，并受剩余 Run 时间与当前租约约束。操作成功或异常分别保存 SUCCEEDED/FAILED，超出该尝试的 expiresAt 则 TIMED_OUT，不把迟到值返回处理器。只允许原调用归属追加自身尝试的结束事实；这不改变 Run、Step、输出、配额或当前执行令牌。重复落账不改已保存结果。

扫描发现 deadline 已过时，同事务使活动步骤失败、待执行步骤跳过，提升令牌、结束在途调用、保存事件并将 Run 置 FAILED/BUDGET_EXHAUSTED；已有成功输出保留。过期和旧执行者不能保存检查点或申请下一调用。报告仍未发布。

公开 Run.budget 严格沿用 G01 Schema 的 deadline、max*、dataAttempts/modelAttempts/schemaRepairs/retries；实时毫秒/可调用次数仅通过内部 RemainingBudget 传递。测试导出的真实 API Run 用独立 Python JSON Schema 检查，避免公开响应与冻结契约漂移。

验收：可控 Clock 与真实 MySQL 验证并发十二次申请仅八次派发、4+1 模型上限、跨类型共享两次重试、重领保留全局修复/配额、三资产单窗口、现金/窗口变化/旧令牌阻断；118 秒排队后只传剩余两秒，恰到 deadline 拒绝新调用且操作调用数为零；异常与超时保留尝试，迟到/重复落账不改当前步骤。当前默认处理器只做本地确定性准备，零外部行情/模型调用。

G21 再连接实际适配器的动态传输超时、429 Retry-After、401/403 分类与有界退避；本组没有自动重试。G22/G23 再完成取消和完整重启检查点复用。正式源资格及模型报告流程继续按既定顺序推进。

联合验证：后端全量 279 项通过；随后完善派发前复核、计量结束幂等及跨重领修复边界，19 项相关定向回归通过（含最终 8 项预算测试，累计 280 个后端用例）。前端 29 项、类型检查与生产构建、G01 的 24 项拒绝场景、G13/G14 独立数值/哈希检查、真实 Run API Schema 校验均通过。V9—V11 已在开发 MySQL 应用并多次启动校验，未修改既有成功迁移。验收样本均为 SYNTHETIC，无在线行情或模型调用。
